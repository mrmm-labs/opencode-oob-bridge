## Decisions

- **One path per channel.** `/link/<name>`. The name matches `^[a-z][a-z0-9-]{0,23}$`. `chat` is reserved for the bridge on `/link` and refused as a name. A name that is not configured is a 404, the same answer an old relay gives, so a scan learns nothing.
- **The path is in the proof.** `sealUpgrade(secret, now, path)` signs `GET <path>` and `Verifier.openUpgrade(headers, path)` checks it, both with `/link` as the default. A proof made for `/link` fails on `/link/gw` and the other way round. The optional argument is applied to `src/link/frame.ts` and to its copy in `relay/src/shared/frame.ts`, kept equal by `relay/scripts/sync-shared.mjs` and `shared-copy.test.ts`.
- **The label is in every frame.** A frame on a channel is JSON with a string `t` and `ch` equal to the name of the socket it arrives on. The body is signed, so the label cannot be changed. A frame without it, or with another one, is refused with reason `channel` and dropped.
- **Secrets per channel.** The relay reads `LINK_CHANNELS` (comma-separated names) and, for each name, `LINK_CHANNEL_<NAME>_SECRET` and optionally `LINK_CHANNEL_<NAME>_KEY`, with the same `_FILE` form as `LINK_SECRET`. `<NAME>` is the name in upper case with `-` as `_`; the syntax makes that mapping one to one. Config refuses a secret under 32 characters, a name that breaks the syntax or is `chat`, and a secret that equals `LINK_SECRET` or another channel's. The key check of a channel uses the channel's key, the `LINK_KEY` of `/link` does not apply to it and a channel without a key has no key check.
- **One verifier per channel, one nonce cache.** Each channel has a `Verifier` with its own secret and all of them, with the bridge's, share one `NonceCache`. A frame captured on one socket cannot be replayed on another even if two channels were given the same secret (a test builds that case on purpose).
- **Eviction is per channel.** A second connection on a channel closes the first with 4000 and `replaced`. Connections on other channels, and the bridge, are not touched. Failing pending HTTP requests on replacement stays a bridge-only step: channels have no pending requests.
- **Close code 4000 stops a client.** Reconnecting after 4000 only evicts the connection that replaced you. `LinkClient` records `replaced by another client` in its status, logs it and does not schedule a reconnect until `start()` is called again. Every other close and error keeps the backoff.
- **`LinkClient` signs the path of its URL.** It used the constant `/link`. The relay answered 404 to any other path, so no working configuration changes.
- **Shutdown.** `Link.close()` closes every socket it holds, the bridge's and every channel's, with 1001. Replaced sockets already got 4000. Before this change a channel would have been left open; the test starts a bridge and two channels, closes the link and sees 1001 on all three.
- **Backpressure.** None exists on the chat bridge link today: `send` writes to the socket and ignores `bufferedAmount`, and a slow bridge only costs the relay memory until a request times out. This stays a known limit; the bridge is one authenticated peer on a private network and its requests are bounded by in-flight limits. For channels, `sendTo` checks `bufferedAmount` against `channelBufferBytes` (default 1 MiB), and past it the relay closes the channel with 1013 and the reason `slow consumer`, counts `backpressure` and returns false. A close, not a silent drop, because a stream with a hole is worse than a reconnect.
- **Transport only.** The relay passes a verified frame to `onChannel(name, frame)` and sends with `sendTo(name, frame)`, which stamps `ch` and seals with the channel secret. `main.ts` registers no consumer: a frame with none is refused with reason `unrouted`. The HTTP ingress (`POST /ch/<name>/...` forwarded to the connected client, with its own auth and limits) needs a route list, a body limit and an answer path, and it is a second public surface. It goes in the follow-up spec `link-channel-ingress`, which has to say who may call it.
- **404 is the contract of an old relay.** A client that gets 404 on `/link/<name>` knows the relay predates channels. It does not retry fast: it uses the backoff.

## What a client may rely on

- `/link` behaves as before, byte for byte on the wire. The old client against the new relay, and the new client against the old one, both work.
- A channel client is a plain WebSocket client with the three upgrade headers (and the key header when the channel has a key), `ch` in every frame, and a stop on 4000.
- Nothing in the relay forwards a channel frame to the phone or to the chat bridge.
- What is left to the consumer: acknowledgement and ordering of its own frames, and its own liveness frames. The relay pings every socket and drops a dead one.
