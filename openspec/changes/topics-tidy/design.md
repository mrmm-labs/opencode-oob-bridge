## Decisions

- **Same close path.** `closeTopic(id, "tidy")`. An explicit tidy is not stopped by `topics.closeHeadless: false`, which only switches off the automatic close.
- **Age comes from the host.** The session's last busy or idle time, which `SessionInfo` carries as `activeAt`. A session with none is kept: its age cannot be judged.
- **Verdict order.** Current session, a question or permission waiting, working, chat on (all `keep`); unknown to the host (`close`); no activity time (`keep`); idle past the limit (`close`); else `keep`. Chat on is a guard beyond the request: a closed topic is where the chat lives.
- **Unknown still honours the guards.** A slow host also answers nothing, so an unknown session that is working, has chat on or has something waiting is kept. A topic closed by mistake is reopened when its session is used.
- **Map cleanup is stricter than closing.** Only a topic already closed before the run, whose session is unknown, is dropped. A topic closed in this run is not dropped until the next. The file is copied to `<file>.bak-<time>` first.
- **Output.** A plain list, no table: `close` and `keep` lines of the topic name, age and reason, at most 12 each, then the count of the rest. Names are the ones the bridge made, which already follow `redact`.
- **Open in a TUI.** The TUI half already sends the session its window shows (`roots`, from `ctx.ui.router.current()`) with every heartbeat, every 3 s. The control now keeps that per TUI instead of only the last one, and a TUI that stops beating for the presence window (`PRESENCE_MS`) drops out. A session is open when some live TUI shows it. Limits: one session per window, the one on screen; a TUI that closes is noticed after the presence window, not at once.
- **When it closes.** The bridge checks every 10 s. A session's topic is closed when its session is not open in a TUI, not working, has no chat, has nothing waiting, and no event of the session or its subagents was read for `topicSettleMs` (default 2 minutes; the bridge's own start counts as an event). One check per topic reads only what the bridge already holds.
- **Reopen.** Posting to a topic already reopened it first (`thread()`). A message from the user in a closed topic now reopens it too, before it is handled. A topic reopened by the bridge is not closed again for 10 minutes (`reopenDwellMs` in the connector), so a message in an idle session's topic does not make it flap.
- **Two switches.** The connector decides by reason: `start` and `ended` (headless) follow `closeHeadless`, `idle` follows `closeIdle`, `tidy` follows neither. `ended` is no longer immediate: headless sessions are debounced like the rest.
- **Not built: pinning.** The topic pin is not in the Bot API. Options, none chosen: a 🟢 prefix on the topic name (`editForumTopic`; renames topics, which was ruled out; marks but does not pin or reorder); a topic icon (`editForumTopic`; only the dozen stickers the bot may use, which the bridge already uses for projects); a pinned "open sessions" message in General (`pinChatMessage`, edited in place; no renames; shows at most 5 links; costs one message and an edit per change).
- **Not verified live.** The calls were not run against the real API.
- **Log.** `topics_tidy` with `apply`, `idleHours`, the counts, the source (`chat` or `rpc`) and the trace id, plus the existing `telegram_topic_closed` line for each close.
